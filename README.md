# MyLib — AIエージェントと進める個人開発の記録（抜粋）

Go（バックエンド）と Flutter（クライアント）で開発している個人サービス「MyLib」について、
**テックリード／PM の立場でAIエージェントを「チームメンバー」として運用する開発の進め方**を、実際のドキュメントと一部のコードの抜粋でご紹介するリポジトリです。
サービス本体のソースコードは公開していません。

本リポジトリの日本語の文書は、韓国語の原文ドキュメントのうち、公開する範囲を私が選び、日本語化に AI エージェントの支援を受けたものです。

本プロジェクトは、テックリード／PM として行ってきた**設計、運用、レビュー、単体テストから全体テストまでの統括**を、AIエージェントを使ってどこまでオーケストレーションできるかを検証することから始めた個人プロジェクトです。
私は仕様書、開発スペック、開発計画、設計・開発標準、テスト方針を定めてエージェント（Claude Code、Codex CLI）に指示し、結果をレビューします。実装も自分で行いますが、役割の中心は統括にあります。設計判断と最終的な責任は私にあり、エージェントの成果は必ずレビューします。
そのため、本リポジトリで示すコードの行数は私個人が書いた量ではなく、「統括しているプロダクトの規模」です。

## 1. なぜ別リポジトリか

開発で使っているドキュメント（エージェント向けの指示書、開発標準、作業記録）は、もともと**すべて韓国語**で書かれています。
このリポジトリは、その中から採用担当者・技術面接官の方に見ていただく価値があるものを**選んで日本語に翻訳した抜粋集**です。
原文の内容は変えず、個人情報・内部URL・サービスの内部構造に関わる部分のみ省略または一般化しています。

## 3. 設計で意識していること

認証・セッション・不正利用対策など、金融・決済系のバックエンドでも重要になる論点について、どう判断したかを文書化しています（詳細は [`design/`](design/)）。

| 論点 | 実装方針（要約） |
|---|---|
| トークンの無効化 | リフレッシュトークンのローテーション＋`token_version`による即時無効化 |
| 再認証が必要な操作 | 退会・ソーシャル連携の変更は再認証トークンを必須化（ミドルウェアで強制） |
| 退会処理の冪等性 | MongoDBトランザクションを使わず、Redis → ユーザー所有データ → ユーザー文書の順に**冪等に削除**。途中失敗時は同じ操作の再実行で続きから完了 |
| レート制限 | ログイン・再認証・メール送信で**カウンターを分離**。Redis障害時はインメモリにフォールバック |
| OAuth | トークンをURLに載せず**1回限りのコード**で受け渡し。stateはCookieでなくRedisに保存 |
| 内部エンドポイント | readiness は別の管理キーで保護し、失敗時の応答で存在を隠す（cloaking） |
| 同時実行 | ニックネームごとの識別番号（`#0001` 形式）の採番で、同時リクエストによる重複を unique インデックスの衝突として検知し、最大値を読み直して最大3回まで再試行 |

## 4. AIエージェントとの開発の進め方

### 検証してわかったこと（私の実感）

以下は数値で記録した結果ではなく、運用してきた中での私自身の実感です。

- 開発の初期は、仕様とは異なる結果が出たり、重複したコードが生まれたりすることが多く、私が直接修正する場面がありました。
- AIモデルのバージョンアップを重ねるにつれて、そうした手直しは少しずつ減ってきました。
- 計測した記録は残していません。そのため、改善の度合いを数値では示しません。

### 私の役割: チームリード／PM

人のチームでリードや PM が担う仕事を、AIエージェントをメンバーとして運用する形で行っています。

| チームリード／PM の仕事 | 成果物（このリポジトリでの対応） |
|---|---|
| 仕様の整理 | API 仕様・ユーザーフロー・画面のストーリーボード・機能状況の管理（原本は非公開。API 仕様は [`design/auth-api-excerpt.md`](design/auth-api-excerpt.md) に抜粋） |
| 開発計画の策定 | 作業ドキュメントの運用、製品化の準備度レビュー、作業履歴（[`workflow/process/`](workflow/process/)） |
| 設計と開発標準の整備 | アーキテクチャ設計、API レスポンス・エラーコード標準、Go／Flutter の規約（[`design/`](design/)、[`standards/`](standards/)） |
| メンバー（AI）への指示 | エージェント向け指示書の階層（[`workflow/agent-instructions/`](workflow/agent-instructions/)） |
| 品質管理・テスト | テスト基準、CI のゲート、内部アルファの QA チェックリストと結果報告の様式（準備度レビューの構造は [`workflow/process/`](workflow/process/)） |

エージェント（Claude Code など）には、作業の前に必ず**指示書を階層順に読ませます**。

```
ワークスペース指示書 → サブプロジェクト指示書(AGENTS.md) → 正本ドキュメント → 開発標準 → 作業ドキュメント
```

| 人間が決める | エージェントに任せる |
|---|---|
| 仕様と異なる実装にするかどうか（「勝手に変えず、人間に確認」が規則） | 実装コードの作成（方針とレビューは人間） |
| コミットメッセージの承認（提案 → 承認 → コミット） | テストの作成と実行 |
| 着手するかどうか（アイデアはバックログに記録し、着手決定後に設計書を作成） | 実装に伴う関連ドキュメント（API 仕様・機能状況・アーキテクチャ）の同時更新 |
| 凍結したプロジェクトに手を入れるかどうか（指示がなければ変更しない） | — |
| 生成コード（API クライアント等）は**手で直さない**。原因の Swagger 注釈・設定側を直す | — |
| 別のAIによるクロスレビューの結果を判断する | — |
| 実機での動作確認・手動QA | — |

マージの最終的なゲートは、CI とテストの通過です（`go vet`・ビルド・unit／integration テスト）。

ドキュメントの寿命も規則化しています。完了した計画は履歴に1行残して設計書を削除し、「終わったもの」と「放置されたもの」が混ざらないようにしています。

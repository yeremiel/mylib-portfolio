# Go 設計パターン

## インターフェース（Interfaces）

- 型の振る舞いを定義するときは、インターフェースを使う
- インターフェースは、小さく明確な役割だけを定義する
- インターフェースを使うと、コードの結合度を下げ、テストをしやすくできる

## 並行処理（Concurrency）

- 並行処理には、goroutine と channel を積極的に活用する
- 共有リソースへのアクセスは、`sync` パッケージ（例: `Mutex`、`RWMutex`）を使って競合状態を防ぐ
- goroutine 間の通信は、channel を使って安全に処理する

## 遅延実行（Defer）

- ファイルのクローズやロックの解放など、リソース管理は `defer` を使ってすっきり処理する

## ポインタ（Pointers）

- 本当に必要な場合を除き、ポインタの使用は控える
- 可能であれば、値渡しを使う

## Clean Architecture のレイヤー

### HTTP ハンドラー

- ビジネスロジックを直接処理しない
- リクエストの検証とレスポンスの整形のみを担当する
- サービスレイヤーを呼び出す
- ロジックは別のサービスレイヤーに分離する

### サービスレイヤー

- コアとなるビジネスロジックを実装する
- トランザクションを管理する
- ドメインルールを検証する

### リポジトリレイヤー

- データアクセスのみを担当する
- CRUD 操作をカプセル化する

## 依存性の注入（DI）

- 依存性の注入（Dependency Injection）パターンを活用して、コードの柔軟性とテストのしやすさを高める
- 一箇所で集中管理する

## レイヤーの分離

- HTTP ハンドラー、サービスロジック、データアクセスロジックなどをレイヤーに分け、関心事を分離する
- Handler → Service → Repository の流れを厳格に守る

## エラー設計

- カスタムエラー型は `error` インターフェースを実装する
- ドメインごとにカスタムエラーを定義する
- エラーチェーンを維持する
- エラーに十分な文脈情報を含める

# Git ブランチ・コミット規則

## ブランチ戦略

作業の性質に応じてブランチを分けます。

- 機能開発: `feature/<機能名>`
- バグ修正: `fix/<バグ名>`
- ドキュメント作業: `docs/<ドキュメント名>`
- リファクタリング: `refactor/<対象>`
- テスト作業: `test/<対象>`
- その他の作業: `chore/<作業名>`

基本原則:
- ひとつのブランチは、ひとつの目的だけを持つ
- main ブランチで直接作業しない
- 作業完了後に main ブランチへマージする

---

## ブランチを作成する基準

すべての変更が、必ず新しいブランチを必要とするわけではありません。

次の場合にのみ、ブランチを作成します。
- 独立した機能単位の作業
- ユーザーの操作、または API／画面に影響するバグ修正
- 複数ファイルにまたがる構造的な変更
- レビューやロールバックの可能性が必要な変更

次の場合は、既存のブランチまたは main ブランチで作業してかまいません。
- 単純な誤字の修正
- ログメッセージの修正
- コメントやドキュメントの軽微な修正
- コードのフォーマット整理（機能変更なし）

ただし、ブランチを分けない場合でも、コミットメッセージの規則は同じように適用します。

---

## 短命ブランチの運用原則

ブランチは、作業中だけ維持する一時的な単位として扱います。

- マージが完了したブランチは、すぐに削除する
- 24 時間以上維持されているブランチは、作業単位を見直すか分割する
- 目的が不明確になったブランチは、整理して作り直す

ブランチ名は作業目的を説明する用途にのみ使い、
長期的な変更履歴の管理は、コミットログを基準にします。

---

## コミットメッセージ規約

コミットメッセージは、次の形式に従います。

```
<type>(<scope>): <subject>
```

### type（必須）

- `feat`      : 新機能の追加
- `fix`       : バグ修正
- `docs`      : ドキュメントの追加・修正
- `refactor`  : 機能変更を伴わないコード構造の改善
- `test`      : テストコードの追加・修正
- `chore`     : 設定、ビルド、依存関係などのその他の作業
- `perf`      : パフォーマンス改善

### scope（推奨）

変更が発生した範囲を簡潔に示します。
プロジェクトごとの scope 一覧は、各プロジェクトの指示書（CLAUDE.md）を参照します。

### subject（必須）

- **韓国語で記述する**（本プロジェクトの方針）
- 現在形の動詞を使う
- 末尾にピリオドを付けない
- 50 文字以内
- 変更内容を明確に表現する

例（原文では韓国語。ここでは日本語に訳して掲載）:
```
feat(auth): ログイン API を追加
fix(auth): 期限切れ JWT トークンの処理
refactor(repository): MongoDB クエリロジックを分離
docs(api): レスポンス形式を更新
```

---

## Breaking Change

既存の動作と互換性のない変更がある場合は、`!` を使います。

```
feat(auth)!: トークン構造を変更
```

---

## ブランチ名とコミットメッセージ規則の連携

ブランチ名は、コミットメッセージの `type` と `scope` を決める基準として使います。

### ブランチ → type の対応

- `feature/*`   → `feat`
- `fix/*`       → `fix`
- `docs/*`      → `docs`
- `refactor/*`  → `refactor`
- `test/*`      → `test`
- `chore/*`     → `chore`

### ブランチ → scope のルール

- ブランチ名の最初の意味のある単語を scope として使う
- ハイフン（`-`）でつながっている場合は、最初の単語のみを scope にする

例:
- `feature/auth-login`         → `feat(auth)`
- `fix/user-duplicate-email`   → `fix(user)`
- `docs/api-response`          → `docs(api)`
- `refactor/repository-mongo`  → `refactor(repository)`

---

## コミットメッセージの生成ルール（Claude Code）

Claude Code は、コミットを実行する前に、必ずコミットメッセージを先に提案しなければなりません。

提案時には、次の情報を含めます。
- 作業の種類（type）
- 変更の範囲（scope）
- コミットメッセージ（subject）

形式の例:
```
feat(auth): ログイン API を追加
```

ユーザーが承認した場合、または修正を依頼した場合にのみ、実際のコミットを進めます。

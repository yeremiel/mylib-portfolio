# Auth API 設計の抜粋

MyLib のバックエンドの Auth API ドキュメント（韓国語原文、全 1,126 行）から、**設計上の判断が表れている 4 つの節**のみを日本語に翻訳した抜粋です。
エンドポイント全体の仕様は公開していません。

---

## 1. 概要

### トークンの有効期限

- **アクセストークン**: 15 分
- **リフレッシュトークン**: 7 日

### レートリミット

認証系のルートには、一般レートリミットに加えて、次のルールを追加で適用します。すべて IP 基準の固定ウィンドウで、
**ルールごとに Redis のカウンターが別々**にあるため、ひとつのルールを使い切っても他のルールには影響しません。

| ルール | 適用するエンドポイント |
|---|---|
| `auth` | サインアップ、ログイン |
| `reauth` | 再認証、OAuth 再認証、ソーシャル連携の開始・解除、退会 |
| `email` | メール認証の送信、パスワード再設定の依頼 |

- `reauth` は、パスワード確認の窓口なので、ログインと同じ水準に設定します。設定がない場合、または rate が 0 以下の場合は `auth` の値を使いますが、カウンターは `reauth` として別に数えます。
- 上限を超えた場合は、`429 RATE_LIMIT_EXCEEDED` と `Retry-After`（window の秒数）を返します。
- 任意の機能として、有効なログイン DTO を受け取った後に、正規化したメールアドレスを対象とした試行を IP と無関係に制限できます（設計上のトレードオフは[認証・セッション・不正利用対策の設計メモ](security-and-auth.md)を参照）。
- Redis の加算と TTL はアトミックに処理し、障害時は上限付きのローカルフォールバックを使います。

## 2. トークンの更新

**POST** `/api/v1/auth/refresh`

**認証**: 不要（リフレッシュトークンを本文で渡す）

説明: リフレッシュトークンを使い、新しいアクセストークンとリフレッシュトークンのペアを発行します（Refresh Token Rotation）。

### 設計上のポイント

- **Refresh Token Rotation**: 更新時に、既存のリフレッシュトークンは無効化され、新しいトークンが発行されます。古いトークンの再利用を防ぎ、セキュリティを高めます。
- **同時更新**: 保存されている古いトークンとの**アトミックな比較・入れ替え**に成功したリクエスト 1 件だけが、新しいトークンのペアを受け取ります。他の更新・ログアウト・新規ログインが先に状態を変えた場合は 401 を返し、現在のセッションを上書きしたり、復活させたりしません。Redis のエラー時は、トークンを返しません。クライアントは更新を single-flight にまとめ、レスポンスを失っても古いトークンを自動で再利用しません。
- **クライアントとの整合**: Flutter の `TokenInterceptor` は、ソース上、同時更新をひとつにまとめます。これはコード上の互換性の確認であり、新しいサーバーと実際に配布されたアプリでの検証完了を意味するものではありません。
- **発行識別子**: 新しいリフレッシュ JWT には、ランダムな `jti` を入れ、同じ秒に発行しても異なる値になるようにします。`jti` を持たない既存の有効なトークンは、保存値と一致すれば 1 回だけ更新できます。
- **セッションの即時無効化**: パスワードの変更・再設定を行うと、ユーザーの `token_version` が上がり、既存のアクセストークンとリフレッシュトークンは即時に無効になります。退会は、リフレッシュトークンを削除し、ユーザー文書も削除するため、既存のトークンはすべて拒否されます。

### 既知の制約（明記している点）

- リフレッシュトークンは、**ユーザーごとに 1 つの保存スロット**です。セッションのファミリー単位での再利用検知と、複数端末のセッション分離は、この設計に含めていません。

### リクエスト本文

```json
{
  "refresh_token": "<refresh_token>"
}
```

### レスポンス例（成功）

```json
{
  "status": "success",
  "code": 200,
  "message": "auth.refresh.success",
  "data": {
    "access_token": "<access_token>",
    "access_token_expires_at": 1704700900,
    "refresh_token": "<refresh_token>",
    "refresh_token_expires_at": 1705305700
  },
  "metadata": {
    "timestamp": "2026-01-07T09:00:00+09:00"
  }
}
```

### エラーコード

| HTTP | error | 説明 |
|---|---|---|
| 400 | REQUEST_INVALID | リクエスト形式のエラー（`refresh_token` がない） |
| 401 | AUTH_REFRESH_TOKEN_INVALID | 署名が無効、トークンの種別が refresh ではない、Redis の保存値と不一致、ユーザーが存在しない・無効、`token_version` の不一致（**原因は区別しない**） |
| 401 | AUTH_REFRESH_TOKEN_EXPIRED | 期限切れのリフレッシュトークン |
| 500 | INTERNAL_ERROR | サーバー内部エラー |

## 3. 再認証のヘッダー規約

重要な API は、認証ミドルウェアの後ろに `middleware.RequireReauth` を付けて、再認証を要求します。

```http
DELETE /api/v1/auth/account
Authorization: Bearer <access_token>
X-Reauth-Token: <reauth_token>
```

### 再認証トークンの性質

- `reauth_token` は、不透明なランダム文字列（32 バイト、base64url）です。サーバーは**原文を保存せず、SHA-256 ハッシュのみ**を Redis のキーとして保存します（TTL 5 分）。
- 発行された**ユーザー本人にのみ**有効です。他のユーザーのトークン、期限切れのトークン、使用済みのトークンは、**すべて同じレスポンス**で拒否します（原因を区別しません）。
- トークンは**ハンドラーの実行前に消費**されます（Redis の `GETDEL`。同時リクエストのうち 1 件だけが通過）。その後の処理が失敗しても同じトークンは再利用できないため、再認証からやり直します。
- 他のユーザーに提示されたトークンも、その時点で消費されて破棄されます。
- トークンは、ログや保存先に残さず、発行後すぐに重要な API の呼び出しに 1 回だけ使います。

| HTTP | error | 説明 |
|---|---|---|
| 403 | AUTH_REAUTH_REQUIRED | ヘッダーがない、またはトークンが無効・期限切れ・消費済み・他のユーザーのもの |
| 500 | INTERNAL_ERROR | 再認証トークンの保存先のエラー |

### 再認証を要求するエンドポイント

| エンドポイント | 備考 |
|---|---|
| `POST /api/v1/auth/oauth/{provider}/link/start` | 連携は**開始時点**で消費する。外部認証が失敗した場合は、再認証からやり直す |
| `DELETE /api/v1/auth/oauth/{provider}` | 連携の解除（最後のログイン手段は拒否） |
| `DELETE /api/v1/auth/account` | 退会 |

### 再認証トークンの取得方法

- パスワードがあるアカウント: パスワードを確認して発行する（`POST /auth/reauth`）
- ソーシャル専用のアカウント: OAuth の再認証を開始 → 外部認証 → ディープリンクで 1 回限りのコードを受け取る → コードを再認証トークンに交換する

どちらの方法でも、同じ保存先に同じ形式のトークンを発行します。

### レートリミットとの関係

再認証が必要なルートでは、再認証用のレートリミット（`reauth`）を、再認証ミドルウェアより**先に**適用します。
そのため、上限を超えたリクエストはトークンを消費せず、429 で終わります。

## 4. 退会

**DELETE** `/api/v1/auth/account`

**認証**: 必要（`Authorization: Bearer <access_token>` ＋ `X-Reauth-Token: <reauth_token>`）

**レートリミット**: 再認証用のレートリミット

説明: 再認証トークンを確認した後、アカウントとユーザーのデータを**即時に削除**します。猶予期間とアカウントの復旧はありません。

```http
DELETE /api/v1/auth/account
Authorization: Bearer <access_token>
X-Reauth-Token: <reauth_token>
```

- リクエスト本文は受け取りません。**互換性の変更**: 以前は本文の `{"password": "..."}` でパスワードを確認していましたが、現在は再認証トークンで本人確認を行います。以前のクライアントが送る本文は無視され、再認証ヘッダーがない場合は `403 AUTH_REAUTH_REQUIRED` になります。
- パスワードアカウントは `POST /auth/reauth`、ソーシャル専用アカウントは OAuth の再認証でトークンを取得します。そのため、**ソーシャル専用アカウントでも退会できます**。
- 認証済みのアクセストークンのユーザーのみが退会されます。

### 退会処理の方式（即時削除）

再認証トークンが消費されると、次の順序で削除します。MongoDB のトランザクションは使わず、各ステップを**冪等**に処理します。

1. **セッション・トークンの無効化（Redis）**: リフレッシュトークン、アカウントのメールアドレスに紐づく認証メール・パスワード再設定の OTP と試行回数のカウンター
2. **ユーザーのデータ（MongoDB）**: ユーザーの ID が一致する、ユーザー所有のデータ
3. **ユーザー文書**: 最後に削除

- 複数のユーザーで共有されるデータは削除しません。退会するユーザーが自分で登録したデータのみを削除します。
- **途中で失敗した場合の再試行**: どのステップで失敗しても `500 AUTH_INTERNAL_ERROR` を返し、後続のステップは実行しません。ユーザー文書が残っているため、同じアクセストークンと**新しい再認証トークン**（以前のものは消費済み）で同じリクエストを再送すると、残りのデータを続きから削除します。そのために、削除が完了するまでは `token_version` を上げません。
- **再認証・OAuth の一時キー**: ユーザー ID では検索できないキーのため、削除ステップには含めません。いずれも短い TTL（5 分・60 秒・10 分）で期限切れになり、ユーザー文書がなければ、そのキーでできる操作（再認証トークンの使用、連携・再認証のコールバック）はすべて失敗します。
- **トークン**: リフレッシュトークンは 1 番目のステップで削除されるため更新できず、削除の完了後は、ユーザー文書がないため、既存のアクセストークンも `401` で拒否されます。
- **再登録**: 削除の直後にメールアドレスが解放され、同じメールアドレスで再び登録できます（新しいユーザー ID になります）。退会したメールアドレスでログインすると、存在しないアカウントと同じ `401` を受け取ります。

### エラーコード

| HTTP | error | 説明 |
|---|---|---|
| 400 | AUTH_ALREADY_WITHDRAWN | 即時削除の導入前にソフトデリートされたアカウント（認証の段階で先に拒否されるため、実際にはほとんど発生しない） |
| 401 | AUTH_TOKEN_REQUIRED / AUTH_TOKEN_MALFORMED / AUTH_INVALID_TOKEN / AUTH_TOKEN_EXPIRED | アクセストークンがない・無効・期限切れ |
| 403 | AUTH_REAUTH_REQUIRED | 再認証ヘッダーがない、またはトークンが無効・期限切れ・消費済み・他のユーザーのもの |
| 404 | AUTH_USER_NOT_FOUND | ユーザーが存在しない |
| 429 | RATE_LIMIT_EXCEEDED | リクエストの上限超過 |
| 500 | INTERNAL_ERROR | 削除中のサーバーエラー。新しい再認証トークンで同じリクエストを送れば再試行可能 |

# バックエンド設計メモ: 認証・セッション・不正利用対策（抜粋）

MyLib のバックエンド（Go）の設計ドキュメント（韓国語原文）から、**認証・セッション・不正利用対策に関わる部分のみ**を日本語に翻訳した抜粋です。
サービスの内部構成（データベースのコレクション名、ドメイン別の詳細など）は省略、または一般化しています。

## 1. リクエストの処理構造

```text
Client
  -> Gin Router
  -> グローバルミドルウェア
  -> Handler
  -> Service
  -> Repository
  -> MongoDB / Redis / 外部 API
```

### グローバルミドルウェアの順序

1. Request ID
2. Gin Logger
3. Recovery（panic からの復旧）
4. Security Headers
5. CORS
6. I18n
7. 一般レートリミット（API v1 のルートグループ全体）

認証系のルートには、一般レートリミットに加えて、**用途別のレートリミット**を適用します。
ログイン・登録用、再認証用（再認証、ソーシャル連携の追加・解除、退会）、メール送信用の 3 種類で、**ルールごとにカウンターを分離**しています。
ひとつのルールを使い切っても、他のルールには影響しません。

## 2. 認証とセッション

- JWT のアクセストークンとリフレッシュトークンを使います（有効期限: アクセストークン 15 分、リフレッシュトークン 7 日）。
- **リフレッシュトークンのローテーション**を採用しています。更新のたびに新しいペアを発行し、古いリフレッシュトークンは無効化します。
- `token_version` の検証により、アクセストークンとリフレッシュトークンを**即時に無効に**できます。
- パスワードのハッシュには bcrypt（cost 12）を使います。

複数の機能が共有するセッションの方針は、独立したパッケージにまとめています。

- パスワードの変更・再設定、ソーシャル連携の解除を行うと、`token_version` を上げ、リフレッシュトークンを無効化します。

## 3. 再認証が必要な操作

重要な操作（ソーシャル連携の開始・解除、退会）には、**再認証トークン**を必須にしています。

- 再認証トークンは、パスワードアカウントでは現在のパスワードの確認によって、ソーシャル専用アカウントでは OAuth の再認証によって発行します。そのため、パスワードを持たないアカウントでも退会できます。
- ミドルウェア（`RequireReauth`）が、認証ミドルウェアとレートリミットの**後ろ**でトークンを検証・消費します。
- OAuth のコールバックは、Redis に保存した state の `purpose`（`login`／`link`／`reauth`）で処理を分けます（ログイン、連携の追加、OAuth による再認証）。

## 4. 退会処理: 即時削除と冪等性

退会は、再認証トークンで本人確認をしたうえで、アカウントとユーザーのデータを**即時に削除**します（猶予期間や復旧はありません）。

MongoDB のトランザクションは使わず、各ステップを**冪等**（同じ操作を何度実行しても結果が変わらないこと）に処理します。順序は次のとおりです。

1. **セッション・トークンの無効化（Redis）**: リフレッシュトークン、メール認証・パスワード再設定の OTP と試行回数のカウンター
2. **ユーザー所有のデータの削除（MongoDB）**: ユーザーに紐づくデータを、所有者の ID で削除
3. **ユーザー文書の削除**: 最後に削除

途中で失敗した場合:

- どのステップで失敗しても、`500` を返し、後続のステップは実行しません。
- ユーザー文書が残っているため、同じアクセストークンと**新しい再認証トークン**（以前のものは消費済み）で同じリクエストを再送すれば、残りのデータを**続きから**削除します。
- そのために、削除が完了するまでは `token_version` を上げません。

その他の性質:

- 削除が完了すると、リフレッシュトークンは更新できず、既存のアクセストークンも、ユーザー文書がないため `401` で拒否されます。
- 削除後はメールアドレスがすぐに解放され、同じメールアドレスで再登録できます（新しいユーザー ID になります）。
- 退会済みのメールアドレスでログインすると、存在しないアカウントと同じ `401` になります（アカウントの存在を明かしません）。
- 再認証・OAuth の一時キーは、ユーザー ID では検索できないため削除の対象にしていません。いずれも短い TTL で期限切れになり、ユーザー文書がなければ、そのキーでできる操作（再認証トークンの使用、連携・再認証のコールバック）はすべて失敗します。

## 5. リクエスト保護

- API v1 の境界で、許可されたクライアント識別子を検証し、クライアントごとにレートリミットをかけます。
- ユーザーのデータを扱うルートでは、JWT 認証とリソースの所有権検証を行います。
- 内部の readiness ルートは、別の管理者キーで保護し、失敗時は**存在を隠すレスポンス（cloaking）**にします。
- `trusted_proxies` の設定で、信頼するプロキシの範囲を制御します。
- Security Headers ミドルウェアを適用しています。
- リクエスト本文のサイズに上限を設けます（既定 1MB、ルート単位で個別の上限を設定可能）。
- レートリミットは Redis を基本とし、**障害時はインメモリにフォールバック**します。
- OAuth のリダイレクト先は、許可リストと**完全一致**で照合します。
- OAuth の結果は**1 回限りのコード**でのみ受け渡します。トークンをリダイレクト URL に露出させないための選択です。state も Cookie ではなく Redis に保存します。アプリの HTTP クライアントは Cookie ベースの state 検証を通過できないためです。
- HTTP サーバーのタイムアウトを設定しています。

## 6. ログイン対象に対するレートリミット（設計上のトレードオフ）

IP 単位の制限だけでは、分散した IP から同じアカウントに試行を重ねる攻撃を抑えられません。
そのため、**同じログイン対象（正規化したメールアドレス）に対する試行**を、IP に関係なく制限する仕組みを任意機能として用意しています。

設計上の判断:

- **既定では無効**です。設定が欠けている場合、または rate が 0 の場合は無効で、既存の設定のままデプロイしても自動的に有効にはなりません。
- 有効にするには、正の window と、**32 バイト以上**の JWT 用サーバーキーが必要です（設定の読み込み時に検証します）。
- メールアドレスの原文は保存せず、用途を区別した **HMAC-SHA256** のカウンターを使います。JWT 署名とは用途を分離していますが、同じサーバーキーを共用する結合は残ります。HMAC は匿名化ではないため、キーにアクセスできる者は、推測したメールアドレスと照合できます。カウンターの識別子は、公開レスポンスやログには出しません。
- アカウントの**存在の有無を区別せず**同じように数えます（DB を引いて分岐しません）。成功したログインも試行に含め、成功してもカウンターは消しません。
- 制限を超えた場合は `429` と `Retry-After` を返します。**既存のセッションの取り消しや、アカウントの永続的なロックは行いません。** 拒否されたリクエストは TTL を延長しません。
- **トレードオフ（明記している点）**: 攻撃者が被害者のメールアドレスの上限を使い切ることで、そのアカウントの**ログイン機能を一時的に 429 にできてしまいます**。持続的な攻撃では、window ごとに再び上限を使い切れるため、ログインできる状態を完全には保証できません。このトレードオフを受け入れたうえで有効化することとし、IP 単位の制限とエッジでの防御も一緒に使います。リスクに応じた追加認証などは、別途設計します。

カウンターのアトミック性と障害時の挙動:

- Redis の Lua スクリプトで、**INCR と TTL の設定をひとつの実行で**処理します。TTL のない古いカウンターに出会った場合は、TTL を復旧します。有効な TTL は、拒否したリクエストでも延長しません。
- Redis のエラー時、または未構成の場合は、**ローカルのフォールバック**を使います。初期化・加算・期限切れの処理を mutex で保護し、最大 10,000 キー、1 秒ごとの期限切れキーの削除を行います。上限に達した場合は、生きている制限を追い出さず、**新しいキーを 429 で拒否**します。そのため、任意の対象が急増してもメモリは抑えられますが、障害中は新規リクエストを受け付けにくくなることがあります。
- プロセスの再起動や Redis の切り替えで、上限が新しく始まることがあります。複数レプリカ全体での合計上限は、ローカルフォールバックでは保証されません。高可用な分散リミッターの代わりにはなりません。

## 7. 運用基盤（抜粋）

- zap による構造化ログ、lumberjack によるファイルログのローテーション
- `X-Request-Id` の生成とレスポンスへの伝播
- panic の復旧と標準エラーレスポンス
- 韓国語・英語の i18n ミドルウェア
- Swagger UI は開発ビルドでのみ提供

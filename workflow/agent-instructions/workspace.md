# ワークスペース指示書（抜粋）

本ドキュメントは、MyLib のワークスペース直下に置いているエージェント向け指示書 `AGENTS.md`（韓国語原文）から、
**開発の進め方に関わる規則の節のみ**を日本語に翻訳した抜粋です。
Claude Code や Codex などのエージェントは、作業の開始時にこのファイルを最初に読みます。
サービスの内部構成にあたる節（ドメイン一覧、内部ドキュメントのパス、デプロイ関連など）は省略しています。

## 1. ドキュメント管理の原則

- 現在の実装と仕様の判断は、**正本（canonical）ドキュメント**を最優先にします。
- ドキュメントと異なる実装が必要な場合は、勝手に変更せず、ユーザーに確認します。
- コードを変更したときは、関連ドキュメント（API 仕様、DB スキーマ、機能状況、アーキテクチャ）も一緒に更新します。
- ワークスペース直下には、プロジェクト間の連携・共通 QA・オーケストレーションに関するドキュメントのみを置きます。
  バックエンドの詳細はバックエンドの `docs/`、Flutter の詳細は Flutter の `docs/` に置きます。
- 凍結したサブプロジェクトは、指示がなければ変更しません。

### ドキュメントの役割

優先順位は「**正本（canonical） ＞ 作業ドキュメント（working）**」です。

| 区分 | 内容 |
|---|---|
| 正本 | `AGENTS.md`、`README.md`、機能状況・アーキテクチャ・API／DB 仕様などの確定した文書 |
| 作業ドキュメント | `docs/plans/` に置く設計書。**実際に着手すると決めた作業のみ**を置きます |
| 記録 | `HISTORY.md`（終わった作業の1行要約）、`IDEAS.md`（未着手のアイデア） |

### 作業ドキュメントの寿命

1. アイデアの段階では、正式な設計書を作りません。残す必要があれば `IDEAS.md` に1〜2行だけ書きます。
2. 着手を決めてから、`docs/plans/` に設計書を作ります。
3. 実装が終わったら、結論を正本ドキュメントに反映し、`HISTORY.md` に1行残したうえで設計書を**削除**します。
   原本は git の履歴に残るため、保管用のコピーは置きません。
4. 方針が変わって破棄する場合も3と同様に処理し、何に置き換わったかを併せて記録します。
5. 着手しないまま残った設計書には、`> ドキュメント状態: 未着手 / バックログ` のマーカーを付け、`IDEAS.md` からリンクします。
   終わった作業のように見せかけません。

整理は、終わった時点でその都度行います。`archived` や `superseded` の表示だけを付けた文書を積み上げません。
そうした文書が増えると、「終わったもの」と「うやむやになったもの」の区別がつかなくなり、結局すべてを開き直すことになるためです。

## 2. 読む順序

エージェントは、作業を始めるときに次の順で確認します。

1. ワークスペースの `AGENTS.md`（このファイル）
2. 作業対象サブプロジェクトの `AGENTS.md`
3. 関連する正本ドキュメント
4. 関連する開発標準（Knowledge Base）
5. 必要な作業ドキュメント

`CLAUDE.md` は互換用のポインタとしてのみ維持します。新しい規則や詳細な指針は `AGENTS.md` に反映します。
ドキュメントの重複による陳腐化を防ぐためです。

## 3. API 連携パイプライン

バックエンドとクライアントの連携は、**バックエンドの API 仕様**を基準にします。

```text
バックエンド Handler の Swagger 注釈・実装
  -> swagger.json を再生成
  -> API ドキュメントを更新
  -> Flutter 側で API クライアントを再生成（make api-update）
  -> Flutter の DataSource / Repository に反映
```

API を変更するときのルール:

- バックエンド: エンドポイントの実装、Swagger 注釈、API ドキュメント、テストを**一緒に**更新します。
- Flutter: 自動生成コードは**直接修正しません**。
- 生成されたクライアントが誤っている場合は、生成物を手で直すのではなく、まずバックエンドの Swagger 注釈・レスポンス型・生成設定を直します。

## 4. 認証・セキュリティの基準

- ユーザー認証は、JWT（アクセストークン＋リフレッシュトークンのローテーション）に従います。
- 公開 API のように運用しません。テストや内部アルファの段階でも、エンドポイントの公開範囲を明示的に制限します。
- 内部・管理者向けのエンドポイントには、ユーザー認証とは別の管理者キーまたは内部アクセス制限を使います。
- OAuth・クライアント識別子・管理者キー・リダイレクト許可リストを変更するときは、バックエンドの API ドキュメントとデプロイ関連ドキュメントを同時に更新します。
- 秘密値は、ローカル／サーバーの環境ファイルまたはシークレット管理にのみ置きます。リポジトリで管理する設定ファイルには、プレースホルダーのみを残します。

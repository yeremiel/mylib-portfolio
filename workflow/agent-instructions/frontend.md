# Flutter クライアント指示書（抜粋）

MyLib の Flutter クライアント向けエージェント指示書 `AGENTS.md`（韓国語原文）から、設計と進め方に関わる規則の節のみを翻訳した抜粋です。

## 1. アーキテクチャ

```text
Screen / Widget -> Provider (Riverpod) -> Repository -> DataSource -> 生成された API クライアント
```

- `lib/core/` には、ネットワーク、ストレージ、ルーター、共通 API クライアントなどのインフラを置きます。
- `lib/features/<feature>/` には、機能ごとの data／domain／presentation の層を置きます。
- Presentation は、画面の状態とユーザーのイベントに集中します。
- Repository は、ドメインの観点での契約を提供します。
- DataSource は、API クライアントの呼び出しと DTO 変換の境界です。
- DataSource から Dio を直接呼び出しません。必ず共通の REST クライアントの Provider を経由します。

## 2. API 生成物のルール

API クライアントの生成コードは、**自動生成物**です。

- 直接修正しません。
- バックエンドの Swagger または生成設定を直して、再生成します。
- 生成結果が誤っている場合は、原因となるドキュメント・Swagger・注釈をたどります。
- 一時的な手動修正がやむを得ない場合は、先にユーザーへ知らせ、必ず後続の整理作業として残します。

API 変更の連携順序:

```text
バックエンドの Handler／Swagger／API ドキュメントを変更
  -> バックエンドで make swagger
  -> Flutter で make api-update
  -> DataSource／Repository／Provider／UI に反映
  -> テストとドキュメントを更新
```

## 3. 認証フロー

- アクセストークンとリフレッシュトークンを、セキュアストレージに保存します。
- Dio のインターセプターチェーンは、トークンの追加、401 時の更新、エラー変換の順序を維持します。
- リフレッシュトークンのローテーションに合わせて、アクセストークンとリフレッシュトークンの両方を更新します。
- OAuth ログインは、バックエンドの authorize エンドポイント、クライアント識別子、リダイレクト／コールバックの設定と併せて検証します。
- iOS の実機ビルドでは、URL スキーム、関連コールバック、外部ブラウザからの復帰フローを確認します。
- PWA とネイティブアプリでは認証後の復帰方法が異なりうるため、テストのチェックリストを分けます。

## 4. 画面・状態管理のルール

- Riverpod の Provider の命名と階層構造は、既存の feature のパターンに従います。
- ウィジェットは、画面構成とインタラクションに集中し、API 呼び出しは Provider／Repository に委譲します。
- ローディング、空の状態、エラー状態、リトライ状態を、画面ごとに明示します。
- ユーザー向けの文言を変更したら、i18n／文言管理の場所を確認します。
- 画面フローが変わったら、機能状況ドキュメントを更新します。必要に応じて UI 設計ドキュメントも更新します。

## 5. テストの基準

変更の範囲に応じて、次の検証を選びます。

| 変更内容 | 検証 |
|---|---|
| 純粋なロジック | 単体テスト |
| Provider の状態 | Notifier／Provider のテスト |
| API 連携 | DataSource／Repository のテスト、またはモッククライアントのテスト |
| ルーティング／認証フロー | ウィジェットテスト、または E2E テスト |
| 影響範囲が広い変更 | `flutter analyze`、`make test` |
| 生成物の変更 | `make api-update` のあと、差分をレビュー |
| フォーマット | `dart format`（生成クライアントは除く） |

CI は、プルリクエストと主要ブランチへの push のたびに、次を実行します。

- `dart format` の検査
- 生成クライアントと `swagger.json` の一致確認
- `build_runner`
- `flutter analyze`
- `flutter test`

E2E テストはブラウザが必要なため、CI では実行しません。
テストが環境の制約で失敗した場合は、失敗の原因と再現コマンドを作業結果に残します。

## 6. エージェントの作業ルール

- ワークスペース直下に、Flutter 専用の設計書を作りません。Flutter のドキュメントは Flutter 側の `docs/` に置きます。
- API 仕様は、バックエンドの API ドキュメントと Swagger を優先します。
- 生成クライアントを手で直すことで問題を覆い隠しません。
- ユーザーによる既存の変更を元に戻しません。
- 機能の実装が終わったら、機能状況と関連するアーキテクチャ／ユーザーフローのドキュメントを一緒に更新します。

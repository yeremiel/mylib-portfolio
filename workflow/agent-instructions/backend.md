# バックエンド指示書（抜粋）

MyLib のバックエンド（Go）向けエージェント指示書 `AGENTS.md`（韓国語原文）から、設計と進め方に関わる規則の節のみを翻訳した抜粋です。
エージェントは、ワークスペース指示書を読んだあとに、バックエンドの作業でこのファイルを読みます。

## 1. アーキテクチャ

```text
Router -> Middleware -> Handler -> Service -> Repository -> MongoDB / Redis
```

- Handler は、HTTP のリクエスト／レスポンス、バインディング、Swagger 注釈に集中します。
- Service は、ビジネスルールとトランザクションの流れを担当します。
- Repository は、MongoDB / Redis へのアクセスのみを担当します。
- DI（依存性の注入）は、ドメインごとの組み立て用パッケージで構成します。
- 共通機能は `pkg/` に置きます。

## 2. API 契約のルール

API を変更するときは、次をまとめて更新します。

1. Handler の実装と Swagger 注釈
2. Service／Repository のテスト
3. ドメイン別の API ドキュメント
4. `swagger.json`（`make swagger` で生成）
5. フロントエンドに影響がある場合は、フロントエンド側で `make api-update`

レスポンス形式は、共通のエンベロープを維持します。

```json
{
  "status": "success",
  "code": 200,
  "data": {},
  "message": "OK",
  "metadata": {
    "timestamp": "2026-06-10T00:00:00Z",
    "requestId": "..."
  }
}
```

失敗レスポンスでは、HTTP ステータスと本文の `code` を一致させ、`error` は `UPPER_SNAKE_CASE` にします。
`status=error` を HTTP 200 で返すことはしません。

## 3. Swagger のルール

Handler に Swagger 注釈を書き、実装後に `make swagger` を実行します。

- レスポンスの型は、実際の JSON の契約と一致させます。
- バイナリ／ファイルのレスポンスは、生成されるクライアントへの影響を確認します。
- Flutter の生成クライアントが誤って生成された場合は、生成物を直接修正せず、Swagger 注釈または生成設定を直します。
- Swagger を変更したら、関連する API ドキュメントも一緒に更新します。

## 4. 認証とセキュリティ

- ユーザーのデータを扱う API は、JWT 認証ミドルウェアを通過する必要があります。
- リフレッシュトークンは**ローテーション**の方式にします。更新時にアクセストークンとリフレッシュトークンの両方を再発行し、既存のリフレッシュトークンは無効化します。
- OAuth の authorize は、登録済みのクライアント識別子とリダイレクトの許可リストを基準に検証します。
- 内部・管理者向けのエンドポイントを、公開エンドポイントのように置きません。管理者キー、内部ネットワーク、認証済みユーザーの制約のうち、明確なアクセス制御を設けます。
- health／readiness のように運用情報が露出しうるエンドポイントは、最小限のレスポンス、または管理者専用のレスポンスに分けます。
- API キー、管理者キー、OAuth シークレット、JWT シークレットは、リポジトリで管理するファイルに実際の値として置きません。

## 5. i18n とエラー

- ユーザーに表示するメッセージは、i18n のメッセージキーと紐付けます。
- 新しいエラーコードは、既存のプリセット形式と命名規則に従います。
- エラーレスポンスの構造を勝手に変更しません。
- 認証・認可の失敗では、情報の露出を最小限にします。必要な場合は、存在の有無を隠すレスポンスを使います。

## 6. テストの基準

変更の範囲に応じて、次の検証を選びます。

| 変更内容 | 検証 |
|---|---|
| ドメインロジック | 関連パッケージの単体テスト |
| ミドルウェア／エラー／i18n | 該当パッケージの単体テスト |
| API 契約の変更 | Handler のテスト、`make swagger` |
| リポジトリ（永続化）の変更 | Repository のテスト、または結合テスト |
| 影響範囲が広い変更 | `make test`（全体） |

テストが環境の制約で失敗した場合は、失敗の原因と再現コマンドを作業結果に残します。

## 7. エージェントの作業ルール

- ワークスペース直下に、バックエンド専用の設計書を作りません。バックエンドのドキュメントはバックエンドの `docs/` に置きます。
- API 仕様の判断は、コードよりも先に、API ドキュメントと Swagger の契約を確認します。
- コードの変更が API 契約を変える場合は、ドキュメントと生成パイプラインまで処理します。
- ユーザーによる既存の変更を元に戻しません。
- 大規模な機能は、まず `docs/plans/` に作業ドキュメントを作り、実装後に正本ドキュメントへ結論を反映します。

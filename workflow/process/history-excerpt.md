# 作業履歴の抜粋（HISTORY）

MyLib では、**終わった計画や、方針が変わってやめた計画を、その時点で 1 項目だけ記録**し、元の設計書は削除します（元の設計書は git の履歴に残ります）。
これは、「終わったもの」と「うやむやになったもの」を区別するための運用です（規則は [`../agent-instructions/workspace.md`](../agent-instructions/workspace.md) を参照）。
ここでは、実際の記録のうち、判断の経緯が読み取れる項目を日本語に翻訳して抜粋します。内部のパス、環境、ベンダー名は省略・一般化しています。

  モックアップを基準に、Flutter 全体のテーマを新しい配色とフォントの組み合わせに入れ替えようとした計画。完了した項目がないまま中断し、2026-07 に別の視覚言語に方向そのものが置き換えられました。

## 2026-09

- **リファクタリングのローカル検証と後続の整備**（完了、別の設計書なし）
  クラウドセッションで行ったリファクタリング（バックエンド PR #12〜#25、フロントエンド PR #8〜#11）を、ローカルの MongoDB／Redis で最終検証しました。回帰はなく、続いて e2e スイートの書き直し、CI での結合テストとデプロイイメージのビルド検証、Flutter 3.47 へのアップグレードと依存関係の更新を終えてから、ステージングに再デプロイしました（バックエンド PR #26〜#28、フロントエンド PR #12〜#18）。

- **Flutter のパレットを別クライアントの基準に切り替える案**（廃止、別の設計書なし）
  2026-09-24 に、共通の基準パレットを別クライアントのものに決め、Flutter への切り替えをバックログに載せました。09-26 にトークンの対応付けとコントラスト検証の草案を作ってみたところ、描画特性の異なる側のパレットから UI のテキストや操作の色をコントラスト基準に合わせて導くと、主要な操作色がオリーブ調になり、状態ごとの背景がベージュに偏るなど、色が濁りました。媒体の特性が異なるため、パレットはクライアントごとに別々に管理することにしました。

- **ログイン手段の管理、即時削除の退会、メール認証の実用化**（完了、ステージングへのデプロイは 2026-09-27）
  ソーシャルログインで、同じメールアドレスのアカウントを自動的に連携する動作をやめ（衝突時は、登録方法を明かさない同じ 409 を返す）、プロフィールから Google／GitHub の連携を追加・解除できるようにしました。重要な操作には、5 分間有効で 1 回限りの再認証トークン（`X-Reauth-Token`）を要求し、ソーシャル専用のアカウントは OAuth で再認証します。退会は即時削除に変え、アカウントの復旧 API とハード削除バッチを取り除きました（バックエンド PR #29、フロントエンド PR #21）。
  続いて、退会時にユーザーが手動で登録したデータを削除していなかった漏れと、再認証系がログイン・登録とレートリミットを共有していた問題を修正し（PR #30）、ユーザーが登録した個別データを、他のユーザーが識別子で参照できてしまう抜け穴も塞ぎました（PR #31）。パスワードの再設定とメール認証の画面に認証コードの入力を追加し（フロントエンド PR #22）、メール送信サービスを切り替えたうえで `email.require_verified` を有効にして、メール認証を実際に強制できる状態にしました。
  実際の受信箱で、登録 → 認証コードの受信 → 認証 → ログインの全体の流れと、ソーシャル連携の追加・解除を、私自身が確認しました。退会 API の互換性のない変更のため、バックエンドとアプリを同時にデプロイしました（バックアップとロールバック用のタグを用意し、ユニークインデックスの衝突はありませんでした）。ソーシャル専用アカウントの OAuth 再認証と退会、実機でのディープリンクからの復帰は、**検証前**です。

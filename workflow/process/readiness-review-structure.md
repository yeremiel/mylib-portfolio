# 製品化準備度レビューの構造（抜粋）

MyLib の「製品化の準備度レビュー」ドキュメント（韓国語原文、約 600 行）から、**判定の仕組み**のみを日本語に翻訳・一般化した抜粋です。
このレビューは、機能の数ではなく、**段階ごとの開始条件・完了条件**で製品の状態を判定するためのものです。
運用に関する詳細（配布対象の識別子、バックアップの保管先など）と、製品の機能範囲は省略しています。

## 1. 結論の書き方

レビューは、冒頭で結論を述べます。

- 現在の状態: 技術プロトタイプを超え、**内部アルファを始められる状態**です。
- ただし、**非公開ベータや外部ユーザー向けの製品として見られる段階ではありません**。
- 不足しているのは、機能の数よりも**検証と運用の根拠**です。たとえば、同じビルドを実際の端末で繰り返し使ったときに、データとセッションが安定しているか、障害時に復旧できるか、配布バージョンを追跡して問題を検知できるか、といった点は、まだ立証されていません。

最初の製品化目標は、次のように固定しています。

> ステージング環境に配布した MyLib を、デスクトップと実際の iPhone で 2 週間、個人の書庫として使い、主要な流れの中断・データの消失・手動でのサーバー復旧なしに使い続けられることを証明する。

## 2. 段階の判定

| 段階 | 判定 | 根拠の種類 |
|---|---|---|
| 内部アルファの開始 | 条件付きで可能 | 主要な API／UI の実装、ローカルテストの通過、ステージングの入口の存在 |
| Web（PWA）での内部アルファ完了 | 未検証 | 現在のビルドでの全体の手動 QA と、2 週間の連続利用の記録がない |
| ネイティブ iOS の内部アルファ | 準備中 | 設定や経路は整っているが、実際の iPhone での全体の流れが未検証 |
| 非公開ベータ | 進入不可 | バックアップからの復旧、可観測性、リリース基準、個人情報のライフサイクル、実ユーザーによる QA が不足 |
| 公開リリース | 範囲外 | ストア配布、運用サポート、ポリシー・法的文書、製品指標が未整備 |

## 3. ゲート（開始条件と完了条件）

段階ごとに、チェックリスト形式のゲートを定義しています。条件は**検証できる事実**として書き、満たしたものだけにチェックを付けます。

### 内部アルファの開始条件（2026-09-28 時点の記録では、すべて充足）

- 配布対象のバックエンド／フロントエンドのコミットを記録した
- バックエンドのテスト、Flutter の analyze／test、Web のビルドが通過した
- リモートの liveness／readiness と、主要 API のスモークテストが通過した
- 認証・メールの流れを、実際のアカウントと受信箱で検証した
- データベースのバックアップを作成し、復旧先を確保した（隔離環境での復元と、原本との一致を確認）
- 現在の検証範囲で、既知の P0 欠陥がない

### 内部アルファの完了条件（記録時点では、すべて未達成）

14 日間の実利用の記録は、まだ開始していません（利用記録のテンプレートのみ用意済み）。

- 14 日間、実際の個人の書庫として使った
- 規定数のデータ（書籍、棚、ウィッシュリスト）で、作成・更新・移動・削除を確認した
- デスクトップと iPhone の PWA で、主要な流れを完了した
- ログアウト、アプリの終了と再起動、アクセストークンの期限切れ後も復旧できた
- データの消失、重複による汚染、他のユーザーへのデータ露出がなかった
- バックアップからの復旧と、以前のビルドの再配布を、それぞれ 1 回成功させた
- 未解決の P0 がなく、P1 は再現手順と優先度が記録されている
- アルファの報告書に、次の決定が記録されている（`アルファ継続`／`ブロッカーの修正`／`ネイティブ iOS アルファ`／`非公開ベータの準備` のいずれか）

### ネイティブ iOS と非公開ベータのゲート（記録時点では、いずれも未達成）

- ネイティブ iOS: 実機へのインストール、起動と再起動、ログイン方式ごとのアプリ復帰、セキュアストレージとリフレッシュトークンのローテーション、カメラ権限、PWA と同じ主要な流れの完了、ネイティブ固有のブロッカーがないこと
- 非公開ベータ: 上記ゲートの通過、配布とテストの CI での再現、自動バックアップ・復旧・監視・アラートの稼働、ステージングと本番の分離、アカウント・個人情報のライフサイクルの一致、テスターの導線、リリースとロールバックの手順の文書化

## 4. 優先度と実行順序

不足している項目は、P0（内部アルファの開始前に閉じる）、P1（ネイティブ iOS、非公開ベータへの準備）、P2（製品リリースの準備）に分けて管理します。

実行順序は、次のように定めています。

1. ドキュメントと自動化の、現在の契約の差を整理する
2. 同じコミットで、ローカルの品質ゲートとリモートのスモークテストを実行する
3. デスクトップの QA は、既存の記録と追加の点検で反映する
4. バックアップと隔離環境での復元を行う
5. 2 週間の内部利用を始め、欠陥と検索の失敗事例を記録する
6. 利用記録に基づいて、機能の範囲と順序を決める。**一部の機能は、私が保留と決めた**
7. ネイティブの実機検証は保留し、再開後に別のゲートとして実行する

## 5. ドキュメントの所有権

判断や手順ごとに、**基準となるドキュメントを一箇所に決めて**います。

| 判断または手順 | 基準となるドキュメント |
|---|---|
| 製品の段階と優先度 | このレビュー |
| アルファの手動 QA | QA チェックリスト |
| アルファの実行結果 | 報告書のテンプレートから作成した、実行ごとの報告書 |
| 配布 | 配布ドキュメント |
| ユーザーフロー | ストーリーボード |
| API の契約とセキュリティ | バックエンドの API ドキュメント |
| DB の構造 | スキーマのドキュメント |
| クライアントの機能・アーキテクチャ | 各クライアントの正本ドキュメント |

詳細な機能状況は、このレビューには**複製しません**。実装が変わったら、まず各サブプロジェクトの正本ドキュメントを直し、製品の段階が変わるときにだけ、このレビューを更新します。

### この構造を選んだ理由

2 つの代替案には、それぞれ問題がありました。

- アルファに関するドキュメントを 1 つのファイルにまとめると、配布、QA、画面フロー、製品判定が混ざり、各サブプロジェクトの正本ドキュメントと重複します。
- 逆に、作業のイシューだけを作ると、なぜその作業が必要なのか、次の段階に進む条件は何かを説明できません。

そこで、このレビューは**段階の判定と、開始条件・完了条件だけを所有**し、実行手順と詳細な状況は、それぞれの正本ドキュメントに置いています。
